## 1. 新しい方向性（企画書の要点）

- **ゲーム**: 駒でコード進行を組み立てる。特徴的なつながり（ドミナントモーション、裏コード、セカンダリードミナント、カデンツ、丸サ・小室などの進行）を「トリック」として判定し、得点・コンボ・演出につなげる。
- **ただし**: 決まった技を成立させることだけが目的になるのは避けたい。想定外の進行も尊重する。教育を捨てず、まず遊びとして面白くする。
- **構成**: いまの物理デバイス（ESP32 + RC522 8台）を、駒を読む入力装置として使い、ゲームは PC のアプリとして別に作る。
- **モード**: フリープレイ / チャレンジ / 対戦。ただし、最初は少数の技で一連の体験を成立させてから広げる。
- **進め方（企画書 6章）**: ① 判定の仕組み → ② 得点・コンボの基本ルール → ③ PC 上の試作（編集・演奏・スコア表示）→ ④ 物理デバイスと接続 → ⑤ 遊んで検証。

## 3. 企画書へのフィードバック

**良い点**
1. 先行事例を正直に整理して、「駒を並べて得点を付けるだけでは独自性が出ない」と、自分で書いている。審査で突っ込まれる点を、先に押さえている。
2. 「決めた技を成立させることだけが目的になるのは避けたい」という問題意識が、研究と合っている。Studley らは、ゲーム性を強めると音楽制作への集中が妨げられる場合がある、と報告している **[調査]**。
3. 「少数の技で、一連の体験を先に成立させる」という進め方が現実的。

**直したい点**
1. **核になる1文が、まだない。** 例: 「駒を並べると進行が鳴り続け、技が決まった瞬間に演出が出て、制限時間内にスコアとコンボを伸ばす」。今の企画書は、制作 → 演奏 → 結果の段階式に読めるが、実機は**常に鳴り続けるループ**で、置き換えるとすぐ音が変わる **[確認]**。これは最大の強みなので、段階式にするか連続式にするかを決める（5-4）。
2. **新規性の書き方が弱い。** 「すべてを統合した先例は確認できていない」は、組み合わせの新しさだけを言っていて、反論されやすい。次のように、機構で書くほうが強い。
   - ① 隣り合うコードの**関係（時間軸）**を判定する。
   - ② 判定の**理由**をその場で説明する。
   - ③ 未定義の進行も、**特徴**で描写して肯定する。
3. **ArchiTone との違いの書き方。** ArchiTone は、和声の機能ごとに形を分ける（正方形=トニック、三角=ドミナント、円=サブドミナント）と説明する記事がある **[調査・二次資料。原文は未精読]**。「機能の可視化」だけでは差にならない。差は、「リアルタイムの判定と理由の提示、駆け引き」に置く。
4. **先行事例の抜け**: タンジブル（触れる）音楽インターフェースの古典、Block Jam（NIME 2003）、Audiopad、Reactable が入っていない **[調査]**。「物理的に音楽を組み立てる」点は、審査で聞かれやすい。
5. **引用の確認**（11章）: ToneCluster の2024年の論文と、ArchiTone の「2026年のプレプリント」は、私の検索では確認できなかった。
6. **評価の計画がない。** 「遊びながら検証する」の、**何を測るか**が書かれていない（5-6 に案）。
7. **対象プレイヤー**: 展示で3分遊ぶ人と、研究の被験者は、同じではない。難易度の設計が変わる。
8. **音楽的な正確さ**: 技の定義（特に丸サ進行の和音）は、資料により違う（5-1）。音楽の分かる人に、確認してもらう。

## 4. Gemini のフィードバックの評価

**同意できる点**
- 4つの課題（判定と尊重のジレンマ / フィードバックの遅れ / 得点基準 / モードの広げすぎ）は、どれも妥当。

**補足したい点（Gemini が知らない・触れていない点）**
1. **「判断材料がない」は、事前の手がかりの問題。** Gemini は「置いた瞬間のフィードバック」で答えているが、メモの趣旨は、置く前に何を頼りに選ぶのか、だと思う。駒のデザイン、ヒント、試し置きなどが別に要る（5-3）。
2. **「ハードの技術リスクが低い」は、条件つきで同意。**
   - 置いてから認識されるまで、約0.3秒かかる **[実測・10/19の記録。今回は再測定していない]**。
   - 隣のリーダーが同じ駒を読む「影」は、対策済みだが、仕組みは証明できていない **[実測]**。
   - 木の盤面・駒の厚みを通して読めるかは、未検証 **[未確認]**。
   - 判定が誤認識に弱いと、体験が壊れる。画面に「認識中」を出す設計が要る。
3. **フィードバックの音は、拍に合わせる。** いまのエンジンは、1ステップ=2拍で進む **[確認]**。置いた瞬間に効果音を鳴らすと、リズムとぶつかる。見た目は即座に、音は次の拍に合わせる（リズムゲームの考え方）。
4. **得点の基準は、数字で作れる**（5-2 の par）。
5. **スケートボードの比喩は、採点の設計に使える**（5-2）。
6. **Gemini の最後の質問（駒の種類・キーはどこまで決まっているか）には、もう答えがある。** 28種+「→」、レベル1〜5、12キー、**判定はキーに依存しない** **[確認]**。足りない駒は、裏コード（♭Ⅱ7）だけ（6-1）。
7. **「モードを1本に」は賛成だが、中身は少し違う。** フリープレイは、何もしなくても存在する（電源ONで自動再生 **[確認]**）。作るのは、実質、**チャレンジ1本**。対戦は、同じチャレンジを交代で遊ぶだけで、新しい仕組みは要らない。

**注意したい点**
- Gemini は、全体に好意的（「非常に妥当」）。実装の現実（認識の遅れ、駒の枚数、盤面の形）には触れていない。

## 5. 設計の提案 **[提案]**

### 5-1. 判定の考え方 — 「性質」と「名前」の2層

名前の付いた技の一覧だけで判定すると、一覧に無い進行は「何も起きない」になる。そこで、2層にする。

**① 性質（すべての進行に付く。駒の度数と種類から計算できる）**

| 性質 | 見るもの | 意味の例 |
|---|---|---|
| 根音の動き | 前のコードから、ルートが何半音動いたか | 5度下行は強い進行（解決感） |
| 共通音 | 前後で共通する音の数 | 多いと穏やか、少ないと意外 |
| 半音で動く音 | 半音で動く声部の数 | なめらかさ |
| 色 | 長音階の外の音の数 | 借用和音・ドミナント系は色が濃い（6-1 の表） |
| 緊張 | ドミナント7・ディミニッシュ・サスの有無 | 緊張 → 解決 |

**② 名前（性質のパターンに名前を付けたもの。得点と演出が付く）**
- 技の定義はデータ（JSON）にして、コードを書かずに足せるようにする。各技に、基本点、必要なレベル、**理由の文**を持たせる。
  - 例: 「Ⅴ7 の シ と ファ が、Ⅰ の ド と ミ に、半音で解決します。緊張から安定へ」。
  - 「どの部分が、どんな理由で評価されたか」を伝えたい（企画書 5章）への答え。
- 一覧に無い進行は、**減点せず**、性質で描写して肯定する（「半音でなめらかに動いた」「意外な借用和音が2つ」）。「芸術点」は付けない（Gemini と同意見）。
  - **（2026-11-16 に変更。ユーザーの指示）**: 「不可解な進行（進行感のない進行）は減点・指摘、名前はないが耳に馴染む進行は加点・指摘してほしい」とのことで、**ルールの審判「ジャッジ」を追加した**（`game/js/core/sense.js`。条件・点数は `docs/judge_report.md`）。描写（ORIGINAL）そのものは、点を変えない。
  - **（2026-11-17 に追加。ユーザーの指示）**: 「流れているメロディに対してコード進行を作り、コード進行としての採点に、メロディとの相性（コードトーン・9th などのテンション・アヴォイドノート）の採点も加えるものを追加してほしい」とのことで、**「メロディにコードをつける」ステージ**を追加した（タイトルの「合わせる」。メロディ5つ。`game/js/core/melody.js`。ルール・点数・限界・確認したい解釈は `docs/melody_mode.md`）。同じ日に、**サス（sus4）の解決（Ⅴsus47 → Ⅴ7）の加点**（ジャッジ G5）と、**プリセット**（気に入った進行の、一部・全部の保存と呼び出し）も追加した。
- 判定は**度数**で行うので、キーを変えても結果は変わらない **[確認]**。

**決めておくこと**
- **度数だけで見るか、コードの種類まで見るか。** 丸サ進行は、資料により、ⅣM7→Ⅲ7→Ⅵm7→Ⅰ7 とされる **[調査: [Wantedly の記事](https://sg.wantedly.com/companies/soundonlive/post_articles/1056523)]**。企画書の「4365」の「5」が、Ⅴ7 か Ⅴm7 かは、私の調べでは確定できなかった。表には、どちらの駒もある（6-1）。
- **ループの最後 → 最初**を、つながりとして数えるか（例: 最後が Ⅴ7、最初が Ⅰ なら、ループの継ぎ目で解決する）。
- **空き・「→」の扱い**: エンジンは、「→」を前のコードの繰り返し、空きを休みとして扱う **[確認]**。判定でも同じ規則にするか、空きでつながりが切れるとするか。

### 5-2. 得点と、動機づけ

- **スケートボードの大会は、難しさ・完成度（execution）・多様さ・流れ（flow）・繰り返し・独創性などで見る**。技の数が多いほど高得点になるとは限らない **[調査: [Red Bull](https://www.redbull.com/us-en/skateboard-contest-scoring-guide)、[ESPN](https://www.espn.com/extreme/s/000401b3org.html)]**。比喩を、そのまま採点の軸にできる。
- **ゲームの前例**: Tony Hawk's Pro Skater は、同じ技を繰り返すと点が下がり（最大で元の10分の1）、違う技を重ねると倍率が上がる **[調査: [Activision サポート](https://support.activision.com/tony-hawks-pro-skater-1-2/articles/tony-hawks-pro-skater-1-2-scoring-and-combos)]**。「定番だけを並べて点を稼ぐ」を防げる。
- **案**: 点 = Σ（技の基本点 × 多様さの倍率 × コンボ倍率）+ 流れのボーナス（ループの閉じ方）。繰り返しは減点。一覧に無い進行は、点は付けず、性質で描写する。
- **ノルマ（目標点）**: ミッションごとに、使える駒で出せる**最高に近い点（par）**を、コンピューターで計算する（動的計画法か探索。未実装）。星1〜3は、par の何割か（例: 40% / 70% / 90%。仮）。「何点を目指せばいいか」に、数字の根拠ができる。
- **聞かせる**: 進行は、**8個の番号**で表せる。短い URL・QR コードにすれば、スマホで聴き直せる（Web 版なら、同じ技術で作れる。**[未確認]**）。会場で、上位の進行を順番に流す。「誰かに聞かせたい」への答え。
- **発見の記録**: 会場の記録に無い進行を作ったら、「初発見」として残す。点数以外の、動機づけ。

### 5-3. フィードバックを4つの層に分ける（メモ1への答え）

| 層 | 例 | 注意 |
|---|---|---|
| **置く前**（手がかり） | 駒の形・色・質感（ポスターのルール）、ヒント表示、**試し置き台**（駒を1つ置くと、その駒の音と、今の盤面とのつながりが出る） | 試し置き台は、リーダーを1台足す必要がある（配線の変更） |

| **終わった後** | 成立した技、理由、コンボ、スコア、進行の共有 | 理由の文を、必ず付ける |

### 5-4. モードと、遊びの形

- **連続式**（私のおすすめ）: ループが常に鳴り続け、置き換えながら遊ぶ。時間切れで結果画面。いまの装置の動きそのもの。**置いた結果が聞こえること自体が、判断材料になる**。
- 段階式（制作 → 演奏 → 結果）: 画面は分かりやすいが、置いた結果が聞こえるのが遅くなる。
- **フリープレイ** = 連続式に、判定の表示を重ねたもの（ほぼ追加なし）。**チャレンジ** = 制限時間・ミッションを足す。**対戦**は、チャレンジを交代で遊ぶ（後回し）。

## 6. 既存システムで確かめたこと

### 6-1. 企画書の技は、いまの駒で表せるか **[確認]**
`python3 tools/game_lab/trick_coverage.py` で、コード表（`src/chords.cpp`）から、再現できる。技の定義は、スクリプト内の**仮の定義**。

**2つのコードのつながり**（同じ駒を並べない 28×27=756 通りのうち）

| 技 | 通り数 | 最小レベル |
|---|---|---|
| ドミナントモーション Ⅴ7 → Ⅰ / ⅠM7 | 2 | 2 |
| **裏コード ♭Ⅱ7 → Ⅰ** | **0（駒がない）** | ― |
| セカンダリードミナント（Ⅰ7→Ⅳ、Ⅱ7→Ⅴ、Ⅲ7→Ⅵm、Ⅵ7→Ⅱm など） | 11 | 3 |
| 偽終止 Ⅴ → Ⅵm | 4 | 1 |
| 変格終止 Ⅳ → Ⅰ | 8 | 1 |

- **♭Ⅱ7 の駒を足すなら、IDは 29**（1〜28 は保存データに書かれているので、意味を変えない。99 は「→」専用）。新しい駒の登録が要る。
- 裏コードの前の「Ⅱ♭M7」は、別のコード（♭Ⅱ△7）。裏コードではない。

**名前の付いた進行**: 小室、王道、カノン、2-5-1、カデンツ、バックドア、ナポリ、丸サ（短い形・長い形）は、**すべて、いまの表だけで作れる**。丸サの長い形に要る Ⅴm7 と Ⅰ7 も、表にある。
- **カノン進行は、同じ駒を2枚ずつ使う**（Ⅰ×2、Ⅳ×2、Ⅴ×2）。駒を1種類1枚にすると、作れない。駒は、タグごと（UID ごと）に登録するので、同じコードのタグを2枚登録すればよい **[確認]**。盤面の「重複」の警告は、同じ**タグ**を2か所で読んだときのもの（同じコードの別のタグではない）**[確認]**。

**「色」の濃い駒**（長音階の外の音の数）: Ⅲ♭m6(3)、Ⅳm7・Ⅵ♭M7・Ⅶ♭7・Ⅱ♭M7・Ⅲ♭M7(2)、Ⅰ7・Ⅲ7・Ⅱ7・Ⅳ#m7-5・Ⅴm7・Ⅴ#dim7・Ⅵ7・Ⅳm6(1)。それ以外（14種）は、長音階の中だけ。

### 6-2. ランダムに並べたら、技はどれくらい出るか **[確認: 計算。仮の定義]**
駒を1種類1枚で、8個（Lv1 だけは4個）をランダムに並べ、上の5つの2コードの技を数えた（20万回、ループの最後→最初も数える）。

| 使う駒 | 技が1つ以上ある確率 | 1枚の盤での技の数（平均） |
|---|---|---|
| Lv1（4種） | 50.0% | 0.67 |
| Lv1〜2（10種） | 68.2% | 0.89 |
| Lv1〜3（15種） | 44.9% | 0.53 |
| Lv1〜4（24種） | 28.7% | 0.32 |
| Lv1〜5（28種） | 24.2% | 0.26 |

- 低いレベルでは、**でたらめに並べても、技が出やすい**。2コードの技だけで点を付けると、「単なるランダム配置」（Gemini の指摘）でも点が入る。点は、**連鎖・多様さ・コンボ**で差を付けるのがよい。
- 一方、特定の4コードの進行（小室など）が、でたらめに出る確率は、**約6万分の1**（8÷(28×27×26×25)）。名前の付いた進行は、狙わないと出ない。

### 6-3. ゲーム側が受け取れるデータ **[確認: コード]**
- ブリッジは、ブラウザに `/api/events`（つなぎっぱなしで届く通知）で、2種類の出来事を送る。`step`（いま始まったステップ）と、`state`（盤面の状態）。
- `state` の `chords` は、位置ごとの `{name: 「Ⅴ7」などの度数の名前, symbol: 「G7」などの実際のコード}`。空き = 「-」、未登録 = 「?」、繰り返し = 「→」。名前は、28種+「→」で重複しない。**IDそのものは送られない**ので、名前から ID への表が要る（ファームのコード表から自動生成して、テストで一致を確認する形が、リズムのプリセットと同じやり方で作れる）。
- ブラウザから操作する API: `/api/control`（BPM・キー・ドラム・バッキング・位置の表・START など）。
- 遅れ: ステップの合図が MIDI から画面まで、中央値 1ms・最大 21ms **[実測・10/19]**。置いてから「置かれた」と認識されるまで約0.3秒 **[実測・10/19の記録]**。

### 6-4. 盤面とループの形 **[確認]**
- 1ステップ = 2拍、最大8ステップ。BPM 120 で、1周 8秒。1小節に1コード（4拍）にしたければ、設定の変更が要る **[未確認]**。
- 位置1〜4 は上段、5〜8 は下段。**位置4 → 5 は、物理的には離れている**（上段の右端 → 下段の左端）。進行の順番と、盤面の形の関係は、`MAP`（位置とリーダーの対応表）で変えられる **[確認]**。ゲームの見せ方に合わせて決められる。

## 7. Unity か、Web（ブラウザ）か **[提案]**

| 観点 | Web（ブラウザ） | Unity |
|---|---|---|
| **既存の仕組みとのつなぎ** | すでに、ブリッジがページと通知を配っている **[確認]**。そのまま延長できる | ブリッジから Unity へ、通信（WebSocket・UDP など）を足す。または、Unity が MIDI を直接扱う。Unity には、MIDI の標準機能がない。[RtMidi for Unity](https://www.npmjs.com/package/jp.keijiro.rtmidi)（出力に対応、Mac の Apple Silicon 対応）や、[Minis](https://www.npmjs.com/package/jp.keijiro.minis)（入力のみ）を使う **[調査]** |
| **試作の速さ** | 保存して再読み込みするだけ | エディタでの操作・ビルドが要る |
| **私との進めやすさ** | コードは全部テキスト。ヘッドレス Chrome で、自動テストと、画面のスクリーンショット確認ができる **[確認: すでに使っている]**。見た目を見ながら直せる | シーン・Prefab・アニメーションは、GUI での作業が中心。私は画面を確認できず、作業が止まりやすい |
| **演出の表現力** | 2D、簡単な3D、パーティクルは十分（Canvas / WebGL など） | 3D・パーティクル・ポストエフェクトは強い |
| **展示・配布** | Mac で Chrome を全画面。進行の共有（URL・QR）も同じ技術 | ビルドが必要（WebGL 書き出しもある） |
| **音** | 駒の音は、いまのとおり ESP32 → MIDI → GarageBand（AUMIDISynth）。効果音は、ブラウザの音機能か、ブリッジ経由の MIDI。**Web MIDI は、Chrome・Edge・Firefox（108以降）で使える。Safari は非対応** **[調査: [caniuse](https://caniuse.com/midi)]**。Chrome を使えばよい | 同じ MIDI が使える |
| **後で乗り換えられるか** | ゲームの中身を「状態を入れたら出来事が出る」独立した部品にしておけば、後で Unity に移せる（C# への書き直しは要る） | ― |

**おすすめ: Web（ブラウザ）。** 理由は、(1) すでに仕組みがある、(2) 試作が速い（先生の「早く見せたい」に合う）、(3) 私が最後まで確かめながら作れる、(4) 共有の仕組みが作りやすい。
**Unity にするなら**: すでに Unity に慣れていて、3D の演出がゲームの核になる場合。その場合も、ゲームの中身は、ブラウザ版と同じ設計（独立した部品）にしておく。
**ToneCluster**（先行事例）のオンライン版は、HTML5 と Unity で開発中と書かれている **[調査: itch.io のページ。完成版の構成かは未確認]**。どちらの道も、先行例がある。
